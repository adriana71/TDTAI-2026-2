# Actividad 2. Organización y documentación del proyecto 🗄️

**Asignatura:** Taller para el Desarrollo de Tecnologías de Automatización I (TDTA I)  
**Unidad:** 2. Organización y documentación del proyecto  
**Modalidad:** Trabajo en equipo  
**Duración:** Semanas 2 y 3  
**Producto:** Expediente inicial del proyecto  
**Valor:** 10 %

---

# 1. Propósito

En la actividad anterior identificaron diferentes oportunidades de automatización en su entorno. A partir de una de esas oportunidades, comenzarán a organizar el proyecto que desarrollarán durante TDTA I.

El propósito de esta actividad es que el equipo establezca una forma sencilla de trabajar, organizar documentos, registrar decisiones y utilizar GitHub para conservar evidencia de sus avances.

Al finalizar deberán contar con un **expediente inicial del proyecto** que permita responder:

- ¿Qué proyecto estamos comenzando?
- ¿Quiénes integramos el equipo?
- ¿Cómo nos vamos a organizar?
- ¿Dónde guardaremos la información?
- ¿Cómo registraremos las decisiones?
- ¿Cómo podremos identificar las aportaciones de cada integrante?
- ¿Qué necesitamos hacer después?

> **Importante:** todavía no deberán diseñar la solución final del proyecto. En esta etapa estamos organizando el trabajo que permitirá estudiar posteriormente el proceso o situación seleccionada.

---

# 2. Producto de la actividad

Durante esta actividad crearán un repositorio de GitHub que funcionará como expediente del proyecto.

Al finalizar deberá contener, como mínimo:

```text
README.md

docs/
└── expediente-inicial.md

evidencias/

bitacora/
└── decisiones.md
```

No es necesario crear desde ahora todas las carpetas que utilizarán durante el semestre. La estructura crecerá conforme avance el proyecto.

# Fase 1. Presentemos nuestro proyecto

Partan de la oportunidad seleccionada en su **Mapa de oportunidades de automatización**.

Creen el archivo:

```text
docs/expediente-inicial.md
```

y agreguen:

```markdown
# Expediente inicial del proyecto

## 1. Identificación del proyecto
```

Completen la siguiente información:

**Nombre provisional del proyecto:**

**Integrantes:**

**Oportunidad seleccionada:**

**¿Qué proceso, situación o necesidad queremos estudiar?**

**¿Por qué nos interesa continuar con esta oportunidad?**

**¿A quiénes podría beneficiar?**

### Antes de continuar

Lean juntos lo que escribieron y respondan:

> ¿Todos los integrantes pueden explicar, con sus propias palabras, de qué trata el proyecto?

Si la respuesta es no, discútanlo antes de continuar.

### Importante

En este momento **no necesitan proponer todavía una solución completa**.

Por ejemplo, no es necesario decidir aún:

- qué sensores utilizarán;
- qué controlador utilizarán;
- qué software desarrollarán;
- qué componentes comprarán;
- cuál será la arquitectura final.

Estas decisiones deberán sustentarse posteriormente con el diagnóstico y la investigación del proyecto.

# Fase 2. Conozcamos y organicemos al equipo

Los integrantes están iniciando su formación en Ingeniería en Automatización. No se espera que cada persona tenga ya una especialidad.

Por ello, antes de repartir responsabilidades, identifiquen qué puede aportar cada integrante y qué le gustaría aprender.

## 2.1 Matriz de capacidades e intereses

Agreguen en `docs/expediente-inicial.md`:

```markdown
## 2. Organización del equipo

### 2.1 Capacidades e intereses
```

Completen:

| Integrante | Algo que considero que puedo aportar al equipo | Algo que me gustaría aprender o mejorar |
| --- | --- | --- |
| ... | ... | ... |
| ... | ... | ... |

No se trata de determinar quién es “el programador”, “el electrónico”, “el mecánico” o “el que escribe”.

La intención es **conocerse para organizarse y aprender juntos**.

---

## 2.2 Roles iniciales

Para comenzar, el equipo utilizará tres tipos de responsabilidades.

### Coordinación

La persona responsable de coordinación:

- ayuda a organizar las actividades;
- da seguimiento a los pendientes;
- verifica que se establezcan responsables y fechas;
- procura que todos participen.

**No es el jefe del equipo y no decide por los demás.**

### Documentación

La persona responsable de documentación:

- verifica que los documentos estén ordenados;
- revisa que puedan localizarse;
- ayuda a registrar acuerdos y decisiones;
- verifica que las evidencias se guarden correctamente.

**No significa que tenga que escribir todos los documentos.**

### Seguimiento en GitHub

La persona responsable del seguimiento en GitHub:

- verifica que el repositorio se mantenga actualizado;
- ayuda a revisar que los commits sean comprensibles;
- verifica que los pendientes importantes estén registrados;
- comprueba que puedan identificarse las aportaciones de los integrantes.

**No significa que deba subir el trabajo de todos.**

Todos los integrantes deberán participar en la comprensión, investigación, discusión y desarrollo del proyecto.

Completen:

| Integrante | Rol inicial | ¿Qué deberá cuidar o verificar? |
| --- | --- | --- |
| ... | ... | ... |
| ... | ... | ... |

Si el equipo tiene dos integrantes, una persona puede asumir dos responsabilidades.

Si tiene más de tres integrantes, dos personas pueden compartir alguna responsabilidad.

> **Los roles son temporales.** En etapas posteriores del proyecto podrán intercambiarse para que todos desarrollen diferentes capacidades.

# Fase 3. Establezcamos nuestros acuerdos de trabajo

Un equipo necesita algunos acuerdos básicos para trabajar.

No se pretende elaborar un reglamento extenso. Discutan las siguientes preguntas y establezcan acuerdos que realmente puedan cumplir.

Agreguen:

```markdown
### 2.2 Acuerdos de trabajo
```

Respondan:

### 1. ¿Cómo nos comunicaremos?

Indiquen el medio principal que utilizarán.

### 2. ¿Cómo distribuiremos las actividades?

Expliquen brevemente cómo decidirán quién participa en cada actividad.

### 3. ¿Qué haremos si alguien no puede cumplir una actividad?

El acuerdo debe permitir avisar con tiempo y reorganizar el trabajo.

### 4. ¿Cómo tomaremos una decisión cuando existan opiniones diferentes?

No es suficiente escribir “por mayoría”. Expliquen qué harán primero para intentar llegar a un acuerdo.

### 5. ¿Cómo revisaremos el trabajo antes de considerarlo terminado?

Indiquen cómo comprobarán que todos conozcan y comprendan lo que se entregará.

Al finalizar escriban:

```markdown
### Nuestro compromiso

Los integrantes discutimos estos acuerdos y nos comprometemos
a utilizarlos durante el desarrollo del proyecto.

Integrantes:
- ...
- ...
- ...
```

# Fase 4. Construyamos nuestro expediente

El **expediente del proyecto** será el lugar donde irán conservando de manera ordenada la información, documentos, evidencias y decisiones que se generen durante TDTA I.

## 4.1 Estructura inicial

Organicen el repositorio de la siguiente manera:

```text
README.md

docs/
└── expediente-inicial.md

evidencias/

bitacora/
└── decisiones.md
```

### ¿Para qué sirve cada parte?

| Elemento | Uso |
| --- | --- |
| `README.md` | Presentación general del proyecto y orientación para quien consulte el repositorio |
| `docs/` | Documentos que se elaboren durante el proyecto |
| `evidencias/` | Fotografías, registros, datos u otras evidencias que posteriormente se obtengan |
| `bitacora/` | Registro de decisiones importantes del equipo |

Agreguen al expediente:

```markdown
## 3. Organización del expediente
```

Expliquen brevemente cómo utilizarán cada carpeta.

---

## 4.2 ¿Cómo nombraremos nuestros archivos?

Acuerden una regla sencilla para evitar archivos con nombres como:

```text
trabajo.docx
nuevo.docx
final.docx
final2.docx
ahora_si_final.docx
```

Por ejemplo:

```text
entrevista-operador-2026-09-15.pdf
diagrama-proceso-2026-09-18.png
registro-visita-2026-09-20.md
```

No es obligatorio utilizar exactamente esta nomenclatura. El equipo puede proponer otra, siempre que sea:

- sencilla;
- comprensible;
- consistente.

Registren su acuerdo en:

```markdown
### 3.1 Regla para nombrar archivos
```

> GitHub conserva el historial de cambios de los archivos. Por ello, no es necesario crear una copia nueva cada vez que se realice una modificación pequeña.

# Fase 5. Creemos nuestra bitácora de decisiones

Creen:

```text
bitacora/decisiones.md
```

La bitácora permitirá recordar **qué decidió el equipo y por qué**.

Utilicen:

```markdown
# Bitácora de decisiones

| Fecha | ¿Qué decidimos? | ¿Por qué? | ¿Quiénes participaron? |
|---|---|---|---|
| ... | ... | ... | ... |
```

## ¿Qué se registra en la bitácora?

Por ejemplo:

| Fecha | ¿Qué decidimos? | ¿Por qué? | ¿Quiénes participaron? |
| --- | --- | --- | --- |
| 05/09/2026 | Continuar con la oportunidad relacionada con el proceso de llenado | Es la oportunidad a la que tenemos mayor posibilidad de acceso | Todo el equipo |

Durante esta actividad deberán registrar **al menos dos decisiones reales** que hayan tomado.

Pueden estar relacionadas con:

- la organización del equipo;
- la oportunidad seleccionada;
- el acceso al proyecto;
- la forma de trabajo;
- algún cambio importante que hayan acordado.

### ¿Qué no es una decisión?

No registren como decisiones:

```text
Hacer la tarea.
Subir el archivo.
Reunirnos.
Buscar información.
```

Esas son actividades o pendientes.

La bitácora deberá permitir responder:

> **¿Qué decidimos y por qué lo decidimos?**

# Fase 6. Organicemos el proyecto en GitHub

GitHub se utilizará como herramienta para conservar el expediente y poder observar cómo evoluciona el proyecto.

No necesitan dominar GitHub para realizar esta actividad.

## 6.1 README

Creen o actualicen:

```text
README.md
```

Incluyan:

```markdown
# Nombre provisional del proyecto

## ¿De qué trata?

## Integrantes

## Oportunidad seleccionada

## Roles actuales

## Organización del repositorio

## Estado actual
```

En **Estado actual** pueden indicar:

```text
El proyecto se encuentra en la etapa inicial de organización
y preparación para comenzar el diagnóstico.
```

---

## 6.2 Contribuciones

Cada integrante deberá realizar **al menos una aportación identificable** al repositorio.

Por ejemplo:

- completar una sección del expediente;
- agregar o mejorar los acuerdos;
- organizar la información;
- crear la bitácora;
- mejorar el README;
- revisar y corregir una sección.

Cada estudiante realizará su propio commit.

Utilicen mensajes que permitan comprender qué hicieron.

Ejemplos:

```text
Agrega organización inicial del equipo
```

```text
Documenta acuerdos de trabajo
```

```text
Crea bitácora de decisiones
```

```text
Actualiza presentación del proyecto
```

Eviten:

```text
cambios
tarea
archivo
actualización
```

> El responsable de seguimiento en GitHub **no debe hacer los commits de los demás integrantes**.

---

## 6.3 Primeros pendientes

Utilicen los **Issues de GitHub** para registrar algunos pendientes importantes.

Durante esta actividad creen al menos **tres Issues**.

Por ejemplo:

```text
Completar expediente inicial
```

```text
Revisar expediente antes de entregar
```

```text
Preparar información para iniciar el diagnóstico
```

Cada Issue deberá indicar:

**¿Qué necesitamos hacer?**

**¿Quién será responsable?**

**¿Cómo sabremos que quedó terminado?**

Cuando un pendiente haya sido atendido, cierren el Issue correspondiente.

> No creen un Issue para cada acción pequeña. Los Issues deben ayudar a recordar pendientes importantes del proyecto.

# Criterios de evaluación

| Criterio | Valor |
| --- | --- |
| Organización del equipo | 25 % |
| Estructura documental | 25 % |
| Trazabilidad de decisiones | 20 % |
| Uso básico del repositorio | 15 % |
| Contribución y calidad | 15 % |
| **Total** | **100 %** |

## Organización del equipo — 25 %

El equipo:

- identifica capacidades e intereses;
- establece responsabilidades iniciales;
- define acuerdos de trabajo;
- establece una forma de resolver desacuerdos;
- comprende que los roles son responsabilidades de organización y no especialidades técnicas.

## Estructura documental — 25 %

El expediente:

- tiene una estructura sencilla y comprensible;
- permite localizar documentos y evidencias;
- utiliza una regla consistente para nombrar archivos;
- puede crecer conforme avance el proyecto.

## Trazabilidad de decisiones — 20 %

La bitácora:

- registra decisiones reales;
- incluye fechas;
- explica por qué se tomó cada decisión;
- identifica quiénes participaron.

## Uso básico del repositorio — 15 %

El repositorio:

- contiene un README comprensible;
- conserva los documentos solicitados;
- utiliza commits descriptivos;
- utiliza Issues para pendientes relevantes.

> GitHub es una herramienta de apoyo para organizar y dar seguimiento al proyecto, no el objetivo principal de TDTA I.

## Contribución y calidad — 15 %

Se evaluará que:

- todos los integrantes tengan aportaciones identificables;
- el expediente sea claro;
- los integrantes conozcan el contenido del proyecto;
- exista participación y corresponsabilidad.

---

# Evidencia individual

Cada integrante deberá poder mostrar en el repositorio **al menos una contribución propia** y explicar:

1. ¿Qué aportó al expediente inicial?
2. ¿Cuál es su responsabilidad actual dentro del equipo?
3. ¿Qué decisión importante ha tomado el equipo hasta ahora?
4. ¿Qué considera que necesitan averiguar a continuación?

> **Organizar el trabajo no significa dividir el aprendizaje. Todos los integrantes deberán poder explicar el proyecto y conocer el contenido general del expediente.**
